# 実装の diff をレビューするとき

OpenCode やサブエージェントが票に沿って済ませた変更を、レビューするときに見る点。Claude が見るときも、Haiku・Sonnet に一次レビューを任せるときも、これを観点として渡す。どれも Sector Dive Extended のレビューや不具合で、実際に漏れたもの。

票どおりか（変更内容の各項目が入っているか、やらないことに書かれた変更が入っていないか）と、STYLE.md に沿っているかは、いつも見る。そのうえで次を見る。

## テスト

- 修正のテストは、修正を外すと落ちることを確かめたか（STYLE.md 8章）
- 保存のテストは、メモリ上の値ではなく保存済みの中身（`localStorage` やセーブのコード）を読んでいるか。メモリ上の値を見ると、浅いコピーのままでも通ってしまう
- テストを分けた・まとめたときは、総数ではなくテスト名で前後を突き合わせたか。`forEach` の中の `test()` などで総数がずれ、抜けに気づけない
- 不安定なテストは、失敗の中身（その時点の状態。Extended の `failInfo`）を出しているか。ファイルをまたいで `localStorage` を共有していないか（ほかのファイルのセーブを読んで、前提が崩れることがある）

## 挙動

- 生成の単位を変えた（区画から建物へ、など）ときは、古い前提（「最初の部屋」「その階の敵ぜんぶ」など）を grep で全部洗ったか
- 設定するときにしか書き込まない値が、次の呼び出しに残らないか。呼び出しの頭で初期化しているか
- 描画の経路が複数あって（建物と固定マップ、など）、直しが1つの経路にしか効いていないことはないか
- 一括置き換えの巻き添え（関係ない物の向き・名前が変わる）を、`git diff origin/master` で見たか
- 足した名前（変数・型・CSS の class）は、既存のものを grep してから付けたか（同じ名前で、テストが全部落ちたり見た目が崩れたりした）

## 報告

指摘ごとに、重さ（重い・中・軽）、場所（ファイルと関数名）、何が起きるか、根拠（読んだコード）、直し方の案を書く。確かめていないことは、確かめていないと書く。
